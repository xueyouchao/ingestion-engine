1 · Overview

The codebase is a small, mostly-clean DDD implementation: domain/ holds value objects and pure policies, application/ holds the one curation use case over four ports, infrastructure/ holds the Common Crawl, engine, language and publishing adapters plus the CocoIndex flow, and interfaces/cli.py drives it. Import direction is respected — no domain module imports application or infrastructure, and no application module imports infrastructure — and the two risky protocol mappings (WARC record → PDF bytes, VLM response → pages) are pure functions with fixture tests. The findings below are therefore about where responsibility sits, not about layering violations: the CocoIndex flow re-implements the curation use case and its failure handling; near-duplicate state is written into flow-owned files by side effect and then clobbered by the next incremental run; the engine registry is not the single source of truth for engine names; and the Document.name field is overloaded between a filesystem path and a URL (leaking a host path into MinerU uploads). None of these are cosmetic, and four of the six are cheap to fix.

2 · Dependency direction

Every solid arrow points inward: interfaces → infrastructure → application → domain, with infrastructure → domain and application → domain as the short paths. Ports live in the domain; infrastructure adapters satisfy them (dashed arrows). The flow (inside infrastructure) assembles the application use case, which is the correct direction — the problem, found below, is that it re-assembles it rather than calling it.

4 · Ranked candidates

Ranked by architectural impact per unit of effort. Effort: S ≈ hours, M ≈ a day or two, L ≈ a week. Every claim cites code read in this review.

  1. 1

    Near-duplicate state is outside the declared target state and is clobbered by the next incremental run

    Effort M

    Change. Stop letting the corpus-wide dedup command rewrite files the flow owns. Either move dedup status into its own declared namespace (out/dedupe/), or make the flow consume the dedup decision instead of defaulting every record to "unique", so that run → dedupe → run is a no-op for dedup state and duplicate Markdown stays deleted.

    Evidence

    • flow.py:90–93 — the flow declares docs/<key>.md and records/<key>.json as target state.
    • domain/publishing.py:50 — dedup_status: str = "unique"; curate.py:136–149 never sets it.
    • infrastructure/publishing/disk.py:87–98 — apply_dedup_plan rewrites each record and doc_path.unlink()s duplicates: a side effect on flow-owned files.
    • docs/adr/0006-…md:33–35 — “re-running run re-publishes candidates and the pass must be run again.”

    Why it matters. The flow’s target state is supposed to be a pure function of the corpus manifest, but the published record’s dedup_status is not: it depends on out-of-band mutation, and re-running the flow (which re-declares the record every time because process_document is not memoised) resets it to "unique" and recreates the duplicate’s Markdown. An operator must know the hidden ordering “run, then dedupe, and never run again” — exactly the “caller must know internal ordering” smell. It also makes the ADR-0006 claim that exact duplicates are a pure function of the manifest only half true once near-duplicates are layered on top.

    Benefit. The incremental guarantee becomes honest: re-running never resurrects dropped documents, and dedup status is reproducible from declared outputs.

  2. 2

    The flow re-implements the curation use case, so there are two orchestrators that will drift

    Effort M

    Change. Give the application one description of “curate an already-extracted document” (record + publish/exclusion branch) and let both CurateDocument.run and process_document call it. The flow keeps only the CocoIndex-specific part — route outside the memo, engine call inside it — instead of re-sequencing route → extract → curate and duplicating failure handling.

    Evidence

    • flow.py:74–99 — manual route (line 75) → use_mount(extract_with_engine) (81–83) → curation.curate(ExtractionResult(...)) (88), with two try/except failure branches.
    • application/curate.py:99–101 — ExtractionStep.extract already composes route + extract; curate.py:123–134 already composes clean + language + judge; curate.py:165–171 already wraps failures into a failed outcome.
    • flow.py:102–108 — _declare_failure duplicates curate.py:169–171’s failure reason formatting in the flow.
    • flow.py:55 & 75 — the PDF is read twice per run (once inside the memo unit, once to route), a concrete symptom of the split.

    Why it matters. ADR-0005’s memo boundary is the only reason the flow cannot call the use case, but that reason is invisible in the code: a future contributor adding a cheap stage will put it in process_document (and it will not be reusable by the dry-run), while the dry-run caller uses CurateDocument.run. The two paths already differ — the flow passes document.url explicitly, the dry-run relies on Document.name — so the same corpus can be described two ways.

    Benefit. One place to change curation; the dry-run and the real flow cannot silently disagree; failure/exclusion wording stops being duplicated.

  3. 3

    Document.name is overloaded between a filesystem path and a URL — and a host path leaks into MinerU uploads

    Effort S

    Change. Make document identity explicit. Either name the field for what it is (url) and pass the PDF path separately where it is needed, or keep name purely as a display filename and have CurateDocument.run(document, url) take the URL as a parameter.

    Evidence

    • infrastructure/cocoindex/flow.py:55 — Document(name=str(pdf_path), …) (a corpus path).
    • interfaces/cli.py:157 — Document(name=document.url, …) (a URL). Same type, different meaning.
    • application/curate.py:168 — url=document.name: the record’s URL is whatever the caller put in name.
    • infrastructure/engines/mineru.py:168–170 — filename = document.name or "document.pdf" becomes the multipart upload filename, so the flow sends /home/…/corpus/pdfs/<digest>.pdf as the filename.

    Why it matters. A caller cannot tell from the interface what name must be, and the dry-run only works because it happens to pass the URL while the flow happens to bypass CurateDocument.run. The MinerU leak is not just untidy: it exposes the pipeline host’s directory layout to the model service and makes the request depend on a path that a different mount point would change.

    Benefit. Unambiguous identity at the seam, and no host path in outbound HTTP requests.

  4. 4

    The engine registry is not the single source of truth: adding an engine touches four files, not one

    Effort S

    Change. Drive the CLI’s engine list/default and the runtime’s native-engine special case from registry.KNOWN_ENGINES / NATIVE_ENGINE, and delete the second "pymupdf" constant. The CLI may import the registry (it is already an outer layer).

    Evidence

    • infrastructure/engines/registry.py:12–16 — NATIVE_ENGINE and KNOWN_ENGINES.
    • interfaces/cli.py:71–72 — hardcoded default="pymupdf" and choices=["pymupdf","docling","paddleocr-vl","mineru"].
    • application/curate.py:23 — a second constant NATIVE_TEXT_ENGINE = "pymupdf".
    • infrastructure/cocoindex/runtime.py:61 & 73 — literal "pymupdf" and build_engines([] if engine_name == "pymupdf" else …).
    • Identity strings are also separate: pymupdf_engine.py:21, docling_engine.py:35, paddleocr_vl.py:34, mineru.py:46.

    Why it matters. ADR-0001 and spec story 13 promise “one adapter module plus one registry entry”. In reality a new engine also needs a CLI choices edit (or it is unreachable by flag) and a runtime default edit; the duplicated "pymupdf" constants can drift. The CLI list cannot be validated against the registry as written, so a typo there fails only at flow-construction time.

    Benefit. The stated extension point actually holds; one list governs flag parsing, defaults and error messages.

  5. 5

    The exact-duplicate decision is implemented three times across three layers

    Effort S

    Change. Have one domain function return, for each URL, its exact-duplicate view (keeper or None plus the exclusion reason), and consume it from both the flow and the dry-run. The corpus-wide plan_deduplication should build on that same view rather than re-deriving it.

    Evidence

    • domain/dedup.py:111–121 — plan_deduplication rebuilds exact DuplicateDecisions from exact_duplicate_keepers.
    • infrastructure/cocoindex/flow.py:115 (compute) + 65–72 (branch, exclusion message).
    • interfaces/cli.py:148 (compute) + 153–156 (branch, same message re-typed).

    Why it matters. ADR-0006 calls exact duplication “a pure function of the corpus manifest”; the rule is shared, but the policy of what a duplicate looks like and says is copied. The dry-run already builds its own Document, so its view can diverge from the flow’s view of the same corpus without any test noticing (only dedup.py is tested against the keeper rule, test_dedup.py:17–22).

    Benefit. One definition of “this document is an exact duplicate of that one”; dry-run and run stay aligned.

  6. 6

    A shallow PageRenderer seam nothing crosses, plus dead work on the corpus-wide dedup pass

    Effort S

    Change. Either use PageRenderer.render inside the PaddleOCR-VL engine or collapse the class to the dpi value it is actually used as, and move it out of the engine factory if it stays. Delete text_by_url and _WORD.

    Evidence

    • registry.py:37–49 defines PageRenderer.render, but the only consumer reads self._renderer.dpi and renders inline (paddleocr_vl.py:44); render() has no call site.
    • paddleocr_vl.py:15 imports PageRenderer from registry.py, so an engine module depends on the engine factory for a helper.
    • domain/dedup.py:123 builds text_by_url (a full dict of every document’s text) and never reads it.
    • domain/dedup.py:13 — _WORD = None, unused.

    Why it matters. PageRenderer is a textbook shallow module — a two-member interface where one member is dead and the other is just an int — and it lives in the wrong file, forcing a registry import from an engine. text_by_url allocates a copy of the entire corpus text precisely on the pass ADR-0006 describes as “cheap, no model calls”.

    Benefit. Fewer hypothetical seams; the dedup pass stops holding the whole corpus text in memory for nothing.

5 · Top recommendation

Make near-duplicate state live in the dedup command’s own declared outputs, and stop writing the flow’s records and Markdown by side effect.

Today apply_dedup_plan (publishing/disk.py:87–98) rewrites records the flow declares (flow.py:90–93) and deletes their Markdown, while the next run re-declares every record with dedup_status="unique" (publishing.py:50) and recreates the deleted file. That makes the incremental target-state claim — the core of the whole design — false in the presence of near-duplicates, and it forces an out-of-band ordering on the operator (ADR-0006 itself admits it). Fixing this first protects the one property the architecture exists to provide; the other five findings are refinements.

6 · Already good — leave alone

  • Direction of dependencies. No domain module imports application/infrastructure, and no application module imports infrastructure (verified by grep over src/finepdfs/domain and src/finepdfs/application). The layering rule genuinely holds.
  • Pure domain policies. text.py, ocr.py, language.py, publishing.py and dedup.py are data + pure functions with no I/O, and the main application test drives them through four hand-written fakes (tests/application/test_curate_document.py:15–50). Good seam, good test surface.
  • Protocol mappings are pure and fixture-tested. WARC → PDF (warc.py:24–40) and the VLM/MinerU/Paddle responses → pages are pure functions tested against recorded fragments (tests/infrastructure/test_warc_record.py, test_vlm_engines.py). Exactly the right risk to pin down offline.
  • Deterministic exact-dedup rule. exact_duplicate_keepers picks the smallest URL per digest, so results are order-independent (dedup.py:36–47; tested at test_dedup.py:17–22). Keep it.
  • Memo boundary direction. The engine call is the memoised unit and the cheap rules sit outside it (flow.py:51–52); a counting engine proves a re-run does not re-extract and a publish-rule change does not re-extract (tests/infrastructure/test_flow_end_to_end.py:146–177). The boundary is right — finding 2 is only about where it is expressed.
  • Deep infrastructure adapters. SubprocessRunner (no shell, PATH check, timeout, clear error) and PdfDocument (context-managed PyMuPDF) hide real work behind small interfaces; the three CLI engines share the runner instead of re-implementing it (subprocess_support.py:30–57).
  • Correct CocoIndex target-state usage in the flow. Outputs are declared with localfs.declare_file, never written directly (flow.py:67–108), and deleting a manifest entry removes its outputs (test_flow_end_to_end.py:205–224). This is the property finding 1 protects.
  • Restraint on speculative ports. No quality-classifier port is introduced until a model exists, and MineruBackend is a real seam with two adapters (HTTP + subprocess), not a hypothetical one. Keep that discipline.
  • Failure isolation and exclusions. One bad fetch or engine call becomes a per-document exclusion with url + reason, and the run continues (fetch.py:66–72; flow.py:76–86, 102–108). Nothing disappears silently, as the spec requires.
  • Environment-only configuration. Because cocoindex update main.py takes no arguments, every knob is a FINEPDFS_* variable and the CLI only sets them (runtime.py:57–91; README.md:91–113). A deliberate, documented constraint, not an accident.
