1 · Overview

At bc0b602 the pipeline is a small, well-layered DDD codebase whose recent redesign moved the whole duplicate decision into the CocoIndex flow: a concurrent first pass (read_document) routes and reads each document and returns its finding as a value, then a single deciding pass (publish_corpus) sees every cleaned text at once and declares either a document’s Markdown + record, an exclusion, or the corpus-wide dedupe/ report. That is a real architectural win: the dedup result is now declared target state, so a re-run cannot resurrect a near-duplicate or overwrite a record — the earlier separate-command design’s central flaw is gone, and ADR-0006, the spec and the README were updated in lock-step. Layering still holds (no domain or application module imports infrastructure or interfaces), the memo boundary is still exactly the engine call, and the risky protocol mappings remain pure and fixture-tested. The findings that remain are narrower: the deciding pass is implemented twice (once in the flow, once in dry-run), the exact-duplicate policy is now spread across four sites (and plan_deduplication’s exact branch is unreachable from the app), Document.name is still overloaded so an absolute host path becomes a MinerU upload filename, and the engine-name list is still duplicated between the registry and the CLI.

Every solid arrow points inward: interfaces → infrastructure → application → domain, with infrastructure → domain and application → domain as the short paths. 4 · Ranked candidates

Ranked by architectural impact per unit of effort. Effort: S ≈ hours, M ≈ a day or two, L ≈ a week. Every claim cites code at bc0b602.

  1. 1

    The deciding pass is implemented twice: publish_corpus and dry-run

    Effort M

    Change. Extract the corpus decision into one application-level pure function — decide_corpus(readings, threshold) -> outcomes/exclusions — that returns values and writes nothing. publish_corpus becomes a thin declarer over that result, and _dry_run prints it. The branch order (exact → failed → dropped → near → published) then exists once.

    Evidence

    • flow.py:116–143 — curates every non-exact reading, calls plan_deduplication, maps near-duplicates, then declares.
    • flow.py:151–190 — _declare encodes the exclusion precedence: exact (159–163), failed (164–166), dropped (168–171), near (173–177), published (179–182).
    • cli.py:157–198 — _dry_run independently curates keepers, calls plan_deduplication (164), maps near-duplicates (172) and re-encodes the same precedence in its print loop.
    • docs/adr/0006-decide-duplicates-in-the-flow.md:56 — “dry-run prints what the deciding pass would decide.” The guarantee is by hand-discipline, not construction.
    • Failure paths also diverge: the flow records a failure string in read_document (flow.py:100–102) while the dry-run relies on CurateDocument.run returning status="failed" (curate.py:165–171).

    Why it matters. This is duplicate domain logic across two layers, and the two copies must agree on a subtle ordering (a document can be both drop-eligible and a near-duplicate; which reason wins is a policy). Today a change to the precedence in _declare silently makes dry-run a lie — the one tool an operator uses to size a GPU job before running. A caller (the CLI) must know the flow’s internal branch order to reproduce it, which is the “caller must know internal ordering” smell at corpus scale.

    Benefit. One corpus decision, testable in memory without CocoIndex; dry-run and run cannot drift; the flow shrinks to “read values, declare results.”

  2. 2

    Document.name is overloaded between a filesystem path and a URL, and a host path leaks as the MinerU upload filename

    Effort S

    Change. Give the document an explicit identity: either rename the field to url and pass the PDF path separately where rendering/upload needs a name, or keep name as a plain display filename (e.g. the content digest) and have CurateDocument.run(document, url) take the URL as a parameter.

    Evidence

    • domain/document.py:10–18 — Document(name, content); nothing says what name is.
    • infrastructure/cocoindex/flow.py:62 — Document(name=str(pdf_path), …), an absolute corpus path.
    • interfaces/cli.py:161 — Document(name=document.url, …), a URL. Same type, different meaning.
    • application/curate.py:168 — url=document.name: the record’s URL is whatever the caller put in name.
    • infrastructure/engines/mineru.py:168–170 — filename = document.name or "document.pdf" becomes the multipart filename=, so the flow uploads /home/…/corpus/pdfs/<digest>.pdf.

    Why it matters. The seam’s contract is ambiguous, and two callers already fill it with different things; the dry-run works only because it happens to pass the URL while the flow bypasses CurateDocument.run and passes the URL explicitly (flow.py:121). The MinerU leak is concrete: it exposes the pipeline host’s directory layout to the model service and makes the request depend on a mount point.

    Benefit. An unambiguous identity at the seam and no host path in outbound HTTP.

  3. 3

    The exact-duplicate policy lives in four places, and plan_deduplication’s exact branch is unreachable from the app

    Effort S

    Change. Have one domain function return each URL’s exact-duplicate view (keeper or None, plus a reason). Use it for the pre-read skip in the flow and for the exclusion, and delete the exact branch from plan_deduplication (or feed it the manifest-level keeper map explicitly) so there is one definition of “this document is an exact duplicate of that one”.

    Evidence

    • flow.py:198 — exact_duplicate_keepers computed in app_main; flow.py:89–90 skips a non-keeper before reading; flow.py:159–163 emits the exclusion.
    • cli.py:154, 159–160, 177–179 — the dry-run recomputes and re-branches the same decision.
    • domain/dedup.py:110–117 — plan_deduplication builds exact DuplicateDecisions from digests.
    • flow.py:123–130 and cli.py:164–171 feed plan_deduplication only published keepers, so its input never contains an exact duplicate — the branch at dedup.py:113–117 is dead in both callers, and flow.py:131 discards every non-near decision anyway.

    Why it matters. ADR-0006 makes exact duplicates “knowable from the manifest alone”, but the policy is now scattered across flow, CLI and domain, while the domain branch is only exercised by a unit test (tests/domain/test_dedup.py:40–53) that no production caller can reach. That is an abstraction kept alive by its test rather than by a caller — YAGNI in reverse.

    Benefit. One exact-dedup definition; less code on the deciding path; the test suite stops certifying dead code.

  4. 4

    The engine registry is not the single source of truth: adding an engine still touches four files

    Effort S

    Change. Drive the CLI’s engine list/default and the runtime’s native-engine special case from registry.KNOWN_ENGINES/NATIVE_ENGINE, and collapse the duplicate "pymupdf" constants into one. The CLI and runtime are already outer layers, so importing the registry is allowed.

    Evidence

    • infrastructure/engines/registry.py:12–16 — NATIVE_ENGINE and KNOWN_ENGINES.
    • interfaces/cli.py:68–69 — hardcoded default="pymupdf" and choices=["pymupdf","docling","paddleocr-vl","mineru"].
    • application/curate.py:23 — a second constant NATIVE_TEXT_ENGINE = "pymupdf".
    • infrastructure/cocoindex/runtime.py:62, 73 — literal "pymupdf" and build_engines([] if engine_name == "pymupdf" else …).
    • Identity strings are separate again: pymupdf_engine.py:21, docling_engine.py:35, paddleocr_vl.py:34, mineru.py:47. Unknown-engine errors are also raised twice (curate.py:57–62, registry.py:85).

    Why it matters. ADR-0001 and spec story 13 promise “one adapter module plus one registry entry”. In practice a new engine also needs a CLI choices edit (or it is unreachable by flag) and a runtime default edit, and the CLI list cannot be validated against the registry as written — a typo there surfaces only when the flow is built.

    Benefit. The stated extension point actually holds: one list governs flag parsing, defaults and error messages.

  5. 5

    Two shallow seams: Runtime rebuilds the use case from step internals, and PageRenderer.render has no caller

    Effort S

    Change. Build CurateDocument once in the runtime and derive the flow’s steps from it (or drop CurateDocument and make the steps the only entry point), removing the pass-through properties. Either use PageRenderer.render inside the PaddleOCR-VL engine or collapse the class to the dpi it is actually used as.

    Evidence

    • runtime.py:50–54 — curator() re-assembles CurateDocument from self.extraction.probe, self.extraction.engines and self.curation.languages.
    • curate.py:78–88, 111–117 — those accessors exist to make that reconstruction possible; runtime.py:40–42 — Runtime.engines has no caller at all.
    • registry.py:37–49 — PageRenderer.render; paddleocr_vl.py:44 reads only self._renderer.dpi and renders inline (pdf.render_page_png). No .render( call site exists.
    • paddleocr_vl.py:15 — an engine module imports the engine factory to get the helper.

    Why it matters. The accessors are interface surface that exists only so Runtime can reach through ExtractionStep; adding a collaborator to a step forces a matching edit in Runtime.curator(). PageRenderer is a textbook shallow module — one method is dead and the other is an int — living in the wrong file.

    Benefit. One assembly path for the use case; fewer hypothetical seams, and an engine no longer depends on the engine factory for a helper.

5 · Top recommendation

Extract the corpus decision into one application-level pure function that both publish_corpus and dry-run consume, so ADR-0006’s promise that “dry-run prints what the deciding pass would decide” becomes structural rather than hand-maintained.

Right now the deciding precedence lives twice — _declare (flow.py:151–190) and the dry-run print loop (cli.py:175–198) — and the two only stay in step by discipline. A single value-returning decide_corpus removes the duplication, keeps the flow as a thin declarer, and makes the decision unit-testable without CocoIndex. It also gives findings 3 and 5 a natural home: the exact-duplicate view and the per-step values move into the same application seam.

6 · Already good — leave alone

  • Duplicates are now declared target state. The deciding pass declares exclusions and the dedupe/{kept,duplicates}.jsonl report (flow.py:136–143, 159–177); nothing is written by side effect, so a re-run cannot resurrect a near-duplicate. Proven end to end (tests/infrastructure/test_flow_end_to_end.py:290–331). This is the branch’s strongest property.
  • Exact duplicates are skipped before the expensive read. read_document returns early for a non-keeper (flow.py:89–90) — a genuinely subtle fix for the fact that concurrency defeats the memo and two identical documents would otherwise both call the engine. Documented in the new ADR-0006.
  • Layering holds. No domain or application module imports infrastructure or interfaces (verified by grep over src/finepdfs/domain and src/finepdfs/application); the outer layers depend inward.
  • The memo boundary is right and proven. Only the engine call is memoised (flow.py:58–63); thresholds and cleaning sit outside it. Counting-engine tests prove a second run does no extraction and a publish-rule change does not re-extract (tests/infrastructure/test_flow_end_to_end.py:147–186).
  • Pure domain policies and pure protocol mappings. text.py, ocr.py, language.py, publishing.py, dedup.py are data + functions, driven with hand-written fakes (tests/application/test_curate_document.py:15–50); WARC → PDF and the VLM/MinerU responses → pages are pure and fixture-tested.
  • Deep infrastructure adapters. SubprocessRunner (no shell, PATH check, timeout, clear error) and PdfDocument (context-managed PyMuPDF) hide real work behind small interfaces; the CLI engines share one runner instead of re-implementing it.
  • Failure isolation. A bad file or a down engine becomes a returned value in read_document (flow.py:100–102) and an exclusion in _declare (164–166); the run continues and nothing disappears silently.
  • Deterministic dedup. The keeper is the smallest URL per digest (dedup.py:35–46) and the near-duplicate plan is a pure function compared in URL order (dedup.py:105–137), tested at tests/domain/test_dedup.py:17–38.
  • Corpus-wide cost is accepted, not hidden. ADR-0006:49–51 and README name the in-memory deciding pass as the price of a corpus-wide decision and scope the pipeline to thousands of documents. That is an honest trade-off, not an accident.
  • Restraint on speculative ports. No quality-classifier port until a model exists; MineruBackend is a real seam with two adapters (HTTP + subprocess). Keep that discipline.
